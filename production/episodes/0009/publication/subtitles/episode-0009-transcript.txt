How do we stop Architectural Intent being lost as software is built? Hello, I'm Russell and welcome to the Articulate Journal where I'm exploring what it takes to build an AI-native architecture from first principles through the design and implementation of a reference architecture for Architectural Intelligence. This isn't a tutorial series or a product demo. It's a public engineering journal documenting the architectural decisions experiments and lessons learned as the architecture evolves. In the last two episodes, we built the conceptual foundation for Articulate. We introduced the Knowledge Model as the place where architectural understanding lives. We also explored how AI can retrieve and reason over that knowledge. At this point, it feels like we've got a good understanding of this part of the architecture. But there's something important missing. Understanding an architecture isn't the same as understanding how it's intended to behave. That raises another question. How do we preserve architectural intent as an idea it becomes running software? Let's imagine we've just finished designing a new capability. We've had conversations with domain experts. We've captured claims in the Knowledge Model. We've reasoned about constraints. We've agreed on the behaviour. Everything feels clear. At that moment, the architecture exists almost perfectly. But only in our current understanding. Now we have to build it. What we really want is surprisingly simple. We want the capability to keep its meaning as it moves through the implementation. We don't want to lose why it exists or outcomes it should produce. The rules it must obey and the policies it operates under and the behaviours that we expect. Ideally, those things should remain true regardless of how we eventually implement the system. That might sound obvious, but it rarely happens. This is where architecture begins to leak. The capability starts life as an architectural idea. Then it becomes a requirement. The requirement becomes backlog items. The backlog items become source code and source code becomes deployments. In an AI-native system, behaviour may disappear even further. Some intent ends up inside prompts. Some becomes workflow definitions. Some is hidden in validation logic and some is scattered across configuration. Some survives only in old documents. By the time the software reaches production, the original architectural intent has been fragmented. The software may work perfectly, but recovering why it behaves that way does become increasingly difficult. This isn't simply a documentation problem. It's a representation problem. While exploring AI-native architecture, I kept running into this problem. The Knowledge Model was excellent for representing what we understood about the architecture, but it wasn't the right place to describe how a capability should behave. That led me to a different question. What if capability behaviour became a first-class architectural concept? Not services, APIs, agents or workflows, capabilities. Capabilities that describe outcomes, behaviour, rules, policies, invariants, effects and life cycle. Without saying anything about implementation, that idea became the foundation of DCL, the Declarative Capability Language. DCL isn't intended to replace source code, and it doesn't replace documentation, and it certainly doesn't replace prompts. Instead, it provides a durable description of architectural intent, one that both humans and AI can understand consistently. This also clarified something else. The Knowledge Model and DCL have different responsibilities. The Knowledge Model represents what Articulate currently understands about an architecture. It can contain uncertainty, conflicting claims, incomplete evidence and knowledge evolves. DCL is different. DCL represents behaviour once the understanding has become sufficiently clear. The progression isn't conversation to DCL. Instead, it becomes conversation, knowledge, understanding, DCL. In this context, the language isn't the starting point. It's the result of architectural understanding. This changes how I think about architecture. A capability is not an API or a service, an agent or a workflow. Those are implementation choices. The capability should survive, even if every one of those technologies changes. Today, a capability might be implemented by deterministic software. Tomorrow, it might use an agent. Next year, it could become a distributed workflow. The implementation evolves, but the capability remains. That's why capabilities feel like much more of a durable architectural building block. This also changes how I think about AI-native systems. It's easy to describe an architecture using agents, whether you've got a research agent, a planning agent, a decision agent or a knowledge agent. But agents are actors. They perform work. They aren't the architectural responsibility itself. The capability is. Once I realized that, the architecture became much clearer. The runtime exists to execute capabilities, not the other way round. At this point, Articulate has three complementary architectural assets. The conversation, which discovers knowledge. The Knowledge Model, which captures architectural understanding, and DCL formalizes capability behaviour. Each solves a different problem. Together, they preserve architectural intent from discovery through to implementation. And that's exactly what we'll need as we move into implementation. Because now, we know what we understand, how we reason, and how capabilities should behave. we can finally ask a different question. What kind of runtime do those capabilities actually need? That becomes the first major architectural decision of the implementation journey. And that is the topic for the next episode. Selecting an agent runtime.
